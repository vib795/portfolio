I wanted a notes app I could talk to.

Not a chatbot stapled to a text box. A real place where everything I capture during the day — a voice memo on a walk, a meeting, a journal entry, a link I want to keep — becomes searchable, so later I can ask “what did I decide about pricing?” and get an answer pulled from my own notes.

I assumed I’d wire it all to a stack of cloud APIs. I was wrong about almost everything, and the app got better because of it.

Here’s the whole thing: how it works, why it’s mostly not in the cloud, what it costs to run, and the security mistake I made along the way.

Point 1 — Almost everything runs on the device. On purpose.

My first plan was simple: call Anthropic for transcription, embeddings, and chat. It died in one afternoon when I hit two walls:

  • Anthropic has no speech-to-text API and no embeddings API. Claude generates beautifully, but it doesn’t turn audio into text or text into vectors — the two things a “capture your life” app leans on most.
  • A Claude Max subscription doesn’t include API access. Different product, metered per token, billed separately.

So I couldn’t just “call the cloud for everything.” And I didn’t want a per-minute transcription bill anyway.

The fix was sitting in iOS the whole time. Apple ships, for free and offline, exactly the two things Anthropic doesn’t sell:

  • Speech recognition (the Speech framework)
  • Sentence embeddings (NLEmbedding)

That flipped the entire design. If something can run on the phone, it does. Transcription, embeddings, search, ranking — all local, all free, all working on a plane. The backend shrinks to one job: hold the secret Claude key (which must never ship inside an app) and relay the generation calls.

[ iPhone — on device ]                        [ Next.js on Vercel ]

  Voice ─▶ Apple Speech ─▶ text ┐
  Typed / journal ──────────────┤
                                ▼
            NLEmbedding.vector() ─▶ store note (SwiftData)

  Ask ─▶ embed query ─▶ local cosine top-k
                  └── {question, notes} ─▶ /api/chat ─▶ Claude ─▶ answer

The phone does the capturing, indexing, and searching. The server passes one message to Claude and hands the answer back. That’s it.

Point 2 — The build, where it counts

It’s a native SwiftUI app (iOS 17+), notes stored on-device in SwiftData. The backend is Next.js on Vercel using the Vercel AI SDK with claude-sonnet-4-6.

Two seams keep it honest:

  • one file names the model and wraps every Claude call
  • one file builds every network request on the device

Change a model? One file. Want to know everything the app sends over the wire? One file.

Capture → text, locally. A voice memo records with AVAudioRecorder and transcribes with Apple's on-device recognizer. No upload. The transcript becomes a note, gets embedded, and is saved — without the phone ever touching my server.

Search, with no vector database. This is the part everyone expects to be hard. NLEmbedding gives a sentence vector on the device; I normalize it and store it next to the note. "My notes" isn't "the internet," so I rank with a plain cosine loop — no Pinecone, no pgvector.

static func score(query: ScoredQuery, against note: StoredNote) -> Double {
    if !query.vector.isEmpty, !note.embedding.isEmpty,
       query.vector.count == note.embedding.count {
        return dot(query.vector, note.embedding)      // cosine for normalized vectors
    }
    return jaccard(query.tokens, tokenize(note.title + " " + note.body))  // graceful fallback
}

If the embedding model returns nothing, it drops to word-overlap instead of going blank. The same function powers “related notes” and the retrieval behind “Ask.”

The one call that leaves the phone. When you ask a question, the device embeds it, ranks your notes locally, and sends Claude only the question plus the handful that matched — never your whole library. The server is stateless: no database, no vectors, nothing stored. It assembles a prompt, calls one model, returns text with [1], [2] citations back to your local notes.

Every route sits behind one bearer-token gate:

export function requireAuth(req: Request): NextResponse | null {
  const expected = process.env.API_TOKEN;
  if (!expected) return null;
  const token = (req.headers.get('authorization') ?? '').replace(/^Bearer\s+/i, '').trim();
  if (token !== expected) return NextResponse.json({ error: 'unauthorized' }, { status: 401 });
  return null;
}

Meetings stretch the same idea to long-form: record in the background, transcribe locally, then one Claude call turns the transcript into a summary, action items, and timestamped topics.

Point 3 — What it actually feels like to use

The point of all this plumbing is that it disappears.

You capture things five ways, and they all land in one on-device list — voice, journal, links, meetings, photos — with open action items and related notes resurfaced automatically.

Open any note and you get its related notes and a “Chat about this note” button. Tap into Ask and you’re talking to your whole library.

It even eats the web. Paste a URL or a YouTube link and it fetches, summarizes (one Claude call), and stores it as a searchable note. Photos get on-device OCR plus a short vision description, so a screenshot becomes something you can find later in plain language.

The pattern repeats so often it is the philosophy: capture and index locally, borrow Claude for the one bit of judgment that needs a frontier model, store the result back on the device.

Point 4 — The economics, and the privacy that comes free with them

Here’s the part that turns architecture into a monthly bill.

English transcription, embeddings, and search are free forever — they’re on-device. The only metered cost is the occasional Claude call (a chat answer, a meeting summary, a link summary). Bounded and rare, not per-minute-of-audio.

But there’s a sharp edge I hit hard: Apple’s on-device recognizer is English-only in practice, and it silently drops other languages. A recording where someone slipped into Hindi mid-sentence came back with the Hindi simply gone — no error. For a memory app, silently losing what someone said is the worst possible bug.

The fix routes Indic languages to a paid provider (Sarvam) — but only when you ask for it. There’s a “Hindi / mixed language” toggle on the capture screens. Its own subtitle says the quiet part out loud: “On-device is English-only & free — turn on for Hindi.”

It defaults on only when the language is set to Hindi, so the common English case never pays by accident.

And privacy? I didn’t bolt it on as a feature. It fell out of the cheapest possible design:

  • Your notes never leave the device — SwiftData on the phone. There’s no notes table on any server, because there’s no database at all.
  • The backend is stateless — it holds the API keys and nothing else. Nothing at rest to breach.
  • Single-tenant by design — one person, one shared token, no accounts, no PII.
  • Most captures never hit the network — an English voice memo is recorded, transcribed, embedded, and stored with zero bytes sent to my server.

The honest trade-off: no cloud backup or multi-device sync yet (an explicit JSON export covers “don’t lose everything”). Real sync means reintroducing a database — and the exact user-data-on-a-server problem I was glad to avoid. That’s the next deliberate decision, not a default.

Bonus: the security mistake, owned

While testing, I fired a quick health check at what I thought was my backend URL — at a domain that turned out not to be mine, with my shared token in the Authorization header. Throwaway request, but the secret was right there in it.

The lesson wasn’t “calculate the odds of a leak.” It was:

  1. Never send a secret to a host you haven’t confirmed you own. “It’s just a health check” is not an exception.
  2. A secret that might be exposed is exposed. Rotate it. I generated a new token, updated the server, redeployed until the old one returned 401, and moved on.

Cheap to rotate. Expensive to assume you got away with it.

What I’d tell you if you’re building one

  • Check what the OS already gives you. I almost paid for two cloud APIs that were sitting in the Speech and Natural Language frameworks the entire time.
  • Let the small corpus be a feature. You don’t need a vector database to rank a few hundred notes.
  • Concentrate the network surface. One file builds every request; one file names the model.
  • Make cost a visible choice, not a hidden one. The Hindi toggle exists so you see when you’re spending money.
  • Treat secrets as radioactive. Keychain on the device, env vars on the server, nothing in the binary, nothing in git — and when in doubt, rotate.

The result feels a little magical: talk to it, then later ask it what you said. Built on a stack that’s mostly not there — no database, no embeddings bill, no per-minute transcription charge, and a server so thin its whole job is to hold one key and pass one message along.

Sometimes the best architecture is the one where the cloud does almost nothing.
