Most developers at work use GitHub Copilot. The best learning resources were built for something else.

There’s a gap that nobody talks about, and I want to close it.

At my company, we have access to Claude models. They’re available right there in GitHub Copilot chat. But Claude Code, the CLI tool that most of the really good AI-assisted development tutorials are built around? Not provisioned. Not going through security review anytime soon. And that’s not unusual — when I ask friends at other firms, the answer is almost always the same: VS Code with Copilot, or IntelliJ with Copilot, or Cursor. That’s the stack. That’s what IT approved, that’s what everybody has open eight hours a day.

So here’s the tension: the best structured learning resource I found for working with AI coding tools — claude-howto, a genuinely well-built tutorial repo — is written for Claude Code and the CLI. It’s excellent if that’s what you use. Most people at work don’t.

I spent a few hours fixing that (thanks to Claude :D).

What I built and why

copilot-howto is a full conversion of that tutorial structure into GitHub Copilot. Same progressive learning approach, same module format, completely rewritten for the tools people actually have in front of them.

Ten modules. Here’s what they cover and, more importantly, why each one matters.

1. Slash commands

Most people treat /explain, /fix, and /tests as shortcuts. They're actually distinct tools with different mental models. /fix works on selected code and assumes context you've already established. /explain works best when you give it scope — a file reference, a selection, a function. Mixing them up produces mediocre output. This module is about learning which one to reach for and when.

2. Custom instructions

This is the one most people completely miss. You can put a .github/copilot-instructions.md file in your repo and it permanently changes how Copilot responds to every member of your team, in that project. Architecture preferences, naming conventions, forbidden patterns, required boilerplate — all of it. No more repeating yourself in every chat message. This single file can do more for team consistency than a style guide nobody reads.

3. Copilot Extensions

Extensions are how you give Copilot capabilities it doesn’t have by default. There are two types: skillset (stateless, single-shot — you call it, it does one thing, done) and agent (conversational, multi-turn, can maintain state). Building a code review extension is roughly 150 lines of Node. This module walks through both types with working scaffolds.

4. Chat variables

@workspace, #file, #selection, #codebase, @terminal — most developers use maybe one of these. Combining them is where things get interesting. Saying using #file:src/auth.ts, explain how @workspace handles session expiry gives Copilot enough context to produce something actually useful instead of a generic answer. This module is entirely about that combination.

5. GitHub Actions integration

Copilot in CI is underused. You can have it auto-review pull requests, flag security issues, generate PR descriptions, run format checks — all without a human in the loop. This module includes five working workflow files ready to drop into any repo.

6. Copilot Workspace

Workspace is GitHub’s task-to-PR tool. You describe what you want changed, it proposes a plan, you refine it, it opens a PR. It’s not magic — the quality of the plan depends heavily on how you write the task. This module covers how to write task specs that don’t produce garbage.

7. The gh copilot CLI

gh copilot suggest and gh copilot explain are genuinely useful and almost nobody knows about them. suggest takes a description of what you want to do in the shell and returns the command. explain takes a command and tells you what it does. If you work with unfamiliar infra tools or write shell scripts occasionally, these save time.

8. Inline suggestions

There’s more here than tab to accept. Next Edit Suggestions can predict your next change based on what you just did. You can configure suggestion delay, enable/disable per language, control trigger behavior. Most of this sits in settings that people have never touched.

9. IDE integration

VS Code, JetBrains, Neovim, Xcode. Each one has different setup steps, different keyboard shortcuts, and different feature gaps. The feature matrix at the end of this module shows which Copilot capabilities are available in which IDE — useful if you work across environments or are evaluating switching.

10. Enterprise configuration

Content exclusion, audit logs, SSO, proxy setup, policy layers. This is for the people who have to manage Copilot across a team or org rather than just use it themselves.

What this isn’t

It’s not a comparison piece. Claude Code is good. If you have it available and want to use it, the original repo it’s based on is worth your time.

This is for the much larger group who shows up to work, opens VS Code, and has GitHub Copilot and nothing else. That group is learning mostly by accident — tab-completing their way through the day, occasionally typing a question into the chat panel, not knowing about half the things the tool can do.

The gap between “using Copilot” and “using Copilot well” is bigger than most people think. Custom instructions alone can change how your whole team works. The CLI tools alone are worth 20 minutes of setup. Extensions are genuinely buildable by one person in an afternoon.

How it’s structured

Each module is a directory with a README and example files — real config, real code, real workflow YAML. Nothing is hand-wavy. The scaffold code in the extensions module runs. The GitHub Actions workflows drop into repos without modification.

The repo has CI that validates all Mermaid diagrams, checks cross-references, runs markdownlint, and builds an EPUB. That last part is overkill, but the structure stays clean because of it.

I’m not claiming this is comprehensive. GitHub Copilot is changing fast enough that some of this will be outdated by the time you read it. But the fundamentals — how context resolution works, why custom instructions matter, when to use which slash command — those are stable enough to be worth learning properly.

If you’re using Copilot eight hours a day and feel like you’re mostly improvising, you probably are. This is for that.
