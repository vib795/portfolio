Two tools (pull-vids + convert-vid), one Mac mini, and a surprisingly painful lesson: the code isn’t the hard part — shipping is.

I didn’t start by trying to “build a home server.”

I started by trying to do a boring thing: download a video, convert it, and watch it later — without fighting a GUI, without manual renames, and without a pile of half-finished files in random folders.

The first few times, I did it manually.

Then I did what every engineer does when a workflow repeats: I turned the pain into a tool.

That turned into two tools.

And those tools turned into a bigger idea: my Mac mini as a personal video pipeline — download, normalize, playlist, stream anywhere.

This looks simple until you ship it.

The problem

My video workflow had a predictable failure mode:

  • Source formats were inconsistent.
  • Output naming was inconsistent.
  • The “I’ll fix it later” pile grew.
  • The one time I needed it on the go, nothing was standardized enough to stream cleanly.

I wanted a workflow that was composable:

  1. Pull content from a URL.
  2. Convert into a consistent format and quality profile.
  3. Organize into a streamable library.
  4. Repeat without babysitting.

Paid apps can do parts of this. They’re often good.

But I wanted something I could automate, script, and run on my own hardware.

So I built two CLIs:

  • pull-vids: downloads from 1000+ sites using yt-dlp (YouTube/Vimeo/TikTok/Twitter/X/IG/Twitch/Reddit + more).
  • convert-vid: FFmpeg-powered conversion for single files or batch directories, with presets and concurrency.

Here’s the part nobody tells you: the “CLI tool” isn’t the product. The install + upgrade path is.

The constraints that actually mattered

I didn’t optimize for novelty. I optimized for repeatability.

1) A single-command experience

If a tool needs a setup guide longer than the tool itself, people stop trying it.

Both tools aim for a single-command UX: one install, one executable.

Under the hood they still orchestrate real engines (yt-dlp / FFmpeg), because reinventing those ecosystems would be irresponsible. The goal isn’t “no dependencies,” it’s “no drama.”

2) Cross-platform builds

I wanted this to work on macOS, Linux, and Windows.

Not because I love edge cases — because I hate rewriting tools when I switch machines.

3) Batch + concurrency without chaos

For conversion, directory workflows are the real test.

  • You need concurrency for speed.
  • You need guardrails so concurrency doesn’t destroy UX, progress, and file integrity.

4) Distribution that doesn’t require “read my README”

Homebrew is the default install path for a lot of devs on macOS, so I shipped both tools via a Homebrew tap:

brew tap vib795/tap
brew install vib795/tap/pull-vids
brew install vib795/tap/convert-vid

This forced me to care about versioning, release artifacts, and checksums.

Which is… where the real work lives.

Here’s the part nobody tells you: distribution is engineering.

The architecture (and why)

At a high level, the system I’m building is a pipeline — not a “media server” first.

Pipeline model

  • Input: URL(s)
  • Download: pull-vids calls into yt-dlp
  • Normalize: convert-vid calls into FFmpeg
  • Organize: folder conventions + playlists (next step)
  • Serve/stream: from the Mac mini (next step)

The tools are intentionally decoupled.

Each does one job well, and the boundary between them is the filesystem.

Why the filesystem boundary is deliberate

It’s boring. That’s the point.

Using files as the interface buys me:

  • Idempotency (re-run safely if outputs exist)
  • Debuggability (inspect intermediates)
  • Composability (swap Jellyfin/Plex/rsync/S3 later without rewriting the core)

The contract I care about is simple: staging is messy, normalized is boring.

Downloads land in a staging folder. Conversions land in a normalized folder with a stable format and predictable naming. If it’s not in “normalized,” it’s not part of the library.

Tradeoff I made: why this isn’t one monolith

Here’s what worked: treat “downloaded file in staging” as a contract.

Here’s what didn’t: mixing “download + convert + organize + stream” into one monolith. That’s a future maintenance trap.

One explicit tradeoff: homebrew-core vs a personal tap (and the rejection that clarified it)

I did try to land pull-vids in homebrew-core first.

The maintainers were polite and direct: the software looks solid, but it doesn’t meet Homebrew’s notability requirements for inclusion in core. They suggested the next step: host it in my own tap, and pointed me to tap docs and best practices.

That response forced a clean decision.

  • homebrew-core is curated. Every formula is long-term maintenance surface area. If you don’t clear the notability bar, it doesn’t matter how clean your code is.
  • A personal tap is the right place to iterate. I control release cadence, can fix packaging issues immediately, and users still get a one-liner install.

So I leaned into the tap — not as a consolation prize, but as the practical distribution path while the project earns real-world usage signals.

The code can be ready before the ecosystem is ready to carry it.

The tricky parts (the stuff that bit me)

1) Versioning drift: “Why is my tool still reporting vdev?”

The easiest way to ship a broken CLI is to compile without embedding version metadata.

This shows up immediately when you install via Homebrew and run:

convert-vid version

…and it prints something like vdev when you expected 1.0.4.

Your users don’t care what your git tag says if your binary doesn’t agree.

Fix pattern: embed version info at build time (GoReleaser helps) and ensure your CLI prints the embedded values (not defaults).

Practically, in Go this usually means injecting version, commit, and date via -ldflags (or letting GoReleaser do it), then wiring your Cobra version command to print those variables.

2) Homebrew formula correctness: tags, checksums, and the “it installs but it’s wrong” problem

Homebrew will happily install whatever artifact you point it at.

If you ship the wrong binary name, the wrong archive layout, or mismatched checksums, you get a fun class of bugs:

  • “It installs but runs the old version.”
  • “It installs but prints vdev.”
  • “It installs but can’t find the expected binary path.”

Fix pattern: treat formula updates like code.

Test locally from a clean state and verify the version string in the installed binary — not just the tag.

3) Concurrency + progress UX: worker pools are easy; correct progress is not

For convert-vid, batch conversion is where things get real.

A worker pool gives throughput. It also creates messy UX:

  • multiple FFmpeg processes emitting output
  • progress bars fighting each other
  • error messages interleaving
  • unclear failure modes when one file fails

Fix pattern: separate concerns:

  • the worker pool does work
  • a coordinator aggregates progress events
  • output is structured and serialized (even if work is parallel)

Here’s representative pseudo-code (conceptual):

jobs := make(chan File)
results := make(chan Result)
for i := 0; i < workers; i++ {
  go func() {
    for f := range jobs {
      results <- convertWithFFmpeg(f, preset)
    }
  }()
}
// enqueue files -> close(jobs) -> aggregate(results) -> print summary

If you don’t do this, you get a tool that’s technically fast and practically unusable.

Parallelism is only a product feature when the output stays readable.

4) AI copilot supervision: Claude Code was helpful… and still needed guardrails

I experimented with Claude Code via antigravity while building this.

It was great for:

  • documentation cleanup
  • refactors
  • repetitive changes
  • “make this section clearer” work

But a couple mistakes slipped in.

In hindsight, some of that was on me:

  • I wasn’t specific enough in prompts.
  • I trusted output too quickly during experimentation.
  • I didn’t constrain changes (tests, build checks, release validation) as hard as I should’ve.

What worked: treat it like a fast junior engineer.

What didn’t: treating it like autopilot.

My rule going forward: AI can touch docs and refactors freely, but anything in the release path (version injection, GoReleaser config, Homebrew formula updates) is manual-review-only.

The implementation highlights

pull-vids: a thin, controlled wrapper over yt-dlp

Core principle: don’t reimplement extractors. Build a great CLI around a proven engine.

Representative invocation (conceptual):

pull-vids "VIDEO_URL" --quality 1080p --audio mp3

The value is in the boring parts:

  • consistent flags
  • predictable output naming
  • progress experience
  • sane defaults

convert-vid: batch conversion with worker pools + presets

Typical workflow:

convert-vid ./downloads --to mp4 --quality medium --recursive

Details that matter:

  • presets map to FFmpeg flags (that mapping is a policy decision)
  • concurrency is bounded (worker pools, not “spawn infinite processes”)
  • progress is aggregated, not spammed

Before vs after (the real improvement)

Before:

  • Manual conversions
  • Inconsistent formats
  • Random filenames and
  • A library that isn’t stream-ready.

After:
A predictable pipeline:

  • downloads land in a staging area
  • conversion normalizes formats + quality
  • output can be organized deterministically (the next build step)

If you only remember 3 things…

  1. Your version string is part of your API. If it lies, everything downstream becomes untrustworthy.
  2. Homebrew distribution forces discipline. That’s good. It will expose your weak spots fast.
  3. Concurrency is only a win if UX stays clean. Parallel work + messy output is a regression.

What I’d do differently next time

1) Build “release verification” into CI from day one

Not just “does it compile,” but:

  • does --version match the tag?
  • does the archive contain the expected binary name?
  • does a tap install produce the expected version output?

That’s the difference between shipping and shipping reliably.

2) Make idempotency explicit in batch workflows

For conversion, I want behavior like:

  • skip files already converted unless --force
  • write outputs to deterministic paths
  • produce a machine-readable report of successes/failures

3) Put tighter guardrails around AI-assisted changes

When using a copilot:

  • smaller diffs
  • more tests
  • explicit “don’t touch release/versioning code” constraints unless necessary

AI can accelerate you into a wall.

Closing

Shipping these two tools taught me something I already knew intellectually but hadn’t fully internalized: the hard part isn’t writing Go.

The hard part is everything around it:

  • versioning that stays honest
  • packaging that stays consistent
  • releases that don’t surprise users
  • concurrency that doesn’t wreck UX

Now I’m rolling those lessons into the next build: repurposing my Mac mini into a personal home server so this pipeline runs while I’m doing anything else.

If you’re building CLIs or shipping side projects, I’d love to hear what bit you hardest: versioning, packaging, distribution, or something else.
