Four rules I built into a memory system for Copilot and Claude Code, after concluding that a confidently wrong note is worse than no note at all.

Open a second window. Your agent knows nothing.

Not less — nothing. The decision you made forty minutes ago about why the queue-based approach was rejected. The constraint that the client’s security team will not approve a new database. The three dead ends you already walked down so you would not have to walk down them again. All of it gone, because context does not survive a window.

So you do the ritual. Paste the chat. Retype what you remember. Re-explain the parts you cannot find. Call it ten to fifteen minutes per switch, plus the premium requests you spend re-deriving conclusions you already paid for once.

Nothing in the platform closes this gap, and it is worth being precise about why:

Every one of those is scoped to the thing you are trying to escape. So I built the memory layer myself — about 2,600 lines of Node, zero runtime dependencies, published as @vib795/agent-memory.

And almost immediately ran into the part nobody warns you about.

Storing more makes it worse

A memory system’s real failure mode is not forgetting. It is remembering wrong, with confidence.

Consider a note that says auth uses JWT, written when that was true, retrieved four months after the codebase moved to server-side sessions. It does not degrade gracefully into uncertainty. It gets retrieved, it gets trusted, and the agent builds on it. You now have an agent that is specifically and confidently wrong, and it has a citation.

That is strictly worse than an agent that says “I don’t know how auth works here.” The second one asks you. The first one ships.

Which means the interesting engineering is not storage. Storage is a directory and a schema. The interesting engineering is the set of guarantees that keep stored knowledge honest while the code it describes moves underneath it.

I ended up with four. Each is a small amount of code and a much larger amount of restraint.

First, a word about who is writing these notes

A language model is. That single fact drives most of the design.

It means the input is untrusted in a specific way — not malicious, but generated from a conversation that may have contained an API key, a connection string, or a colleague’s email address. It means output shape cannot be assumed. And it means every correction round-trip costs a real request.

That last one shows up somewhere you would not expect. In the validator, which reports every problem at once rather than the first:

export function validateNode(input) {
  const e = [];
  // ...every check pushes onto e instead of throwing...
  if (e.length) throw new ValidationError(e);
  return n;
}

Fail-fast validation is the reflex, and it is wrong here. A model correcting its own output fixes everything in one round trip instead of discovering faults one at a time, each costing a premium request. Small change. It is the difference between one retry and five.

Notes come in four types, which will matter shortly: system, decision, convention, and constraint.

Rule 1: Staleness is visible at the moment of use

The JWT-versus-sessions problem cannot be prevented. No amount of design stops a note from being true on Monday and wrong in March.

What you can do is make the age of a note visible at the exact moment someone is about to act on it, which is the only moment anyone can do anything about it.

Every note records the repository HEAD it was captured at:

id: auth-service
type: system
title: Auth uses server sessions
scope: repo
confidence: observed
captured_sha: a1b2c3d      # repo HEAD at capture
repos: [orders-api]
edges:
  - rel: depends-on
    dst: postgres-primary

On retrieval, that becomes a commit count:

captured 47 commits ago — verify before trusting

No model, no scheduled job, no background scanner deciding what is fresh. Just git rev-list --count <sha>..HEAD. Deterministic, and cheap enough to run inline.

Three details did more work than the core idea:

Rebased history says something different. If the commit is unreachable — rebased away, pruned, gone — reporting zero commits would be a lie in the safe direction. It reports history rewritten, verify instead. Unknown is a different answer from fresh, and the two must not be collapsed.

A note only gets annotated in a repo it claims. A commit count taken against unrelated history is noise dressed as a signal. A note scoped to orders-api, retrieved while you are working in billing-api, is left alone rather than flagged as rewritten.

if (Array.isArray(node.repos) && node.repos.length && 
!node.repos.includes(here)) return null;

There is a floor. Below ten commits, staleness is not mentioned at all. A warning that fires constantly is not a warning, it is chrome. The threshold is configurable, and a second, higher one — 100 commits — is what doctor uses to list notes worth a deliberate review, so you can go looking instead of waiting to be told one note at a time.

Rule 2: Redaction is fail-closed

The store is plaintext on a corporate desktop, and its contents were generated by a model from conversations that may have contained anything.

So nothing reaches disk unscanned. Fourteen pattern families — AWS access keys, GitHub and Slack tokens, private keys, JWTs, bearer tokens, connection strings, session cookies, RFC 1918 addresses, internal hostnames — plus email addresses, all replaced with <redacted:kind> before the write.

The word fail-closed is doing specific work, and it is visible in the first three lines:

export function redact(text, opts = {}) {
  if (typeof text !== 'string') {
    throw new TypeError('redact() requires a string; refusing to write unscanned content');
  }

Hand it something it cannot scan and it does not skip the scan and continue. It aborts the write. The failure mode of a redaction pass has to be nothing gets written, never this one got through. There is no bypass flag, because a bypass flag is a thing you will eventually use at 6pm on a Friday.

Two decisions inside it that I would defend:

Connection strings go whole. postgres://user:hunter2@db.internal:5432/orders carries the credential inline, so the entire URI is replaced rather than the password inside it. A partially-redacted URI still hands a reader the host, the port, the database name, and the username.

Assignment-shaped secrets need proof. The naive pattern for password: <something> also eats the sentence "the password rotation policy is 90 days." So the pattern requires quotes or a long unquoted run:

{
  kind: 'assigned-secret',
  re: /\b(?:api[_-]?key|secret|password|token|client[_-]?secret|
access[_-]?key)\b\s*[:=]\s*(?:"[^"\n]{6,}"|'[^'\n]{6,}'|[^\s"'`,;)]{12,})/gi,
}

Redaction that mangles ordinary prose gets turned off. Then it protects nothing.

There is exactly one exception in the whole module: your own git identity survives, because it is already stamped on every commit you have ever pushed. Redacting it buys nothing and makes notes harder to read.

Rule 3: Truncation is never silent

get --depth 2 on a well-connected node can pull back fifty notes and blow the context window this entire design exists to protect. So there is a byte budget — 8 KB by default — and pruning when it is exceeded.

That much is unremarkable. What matters is what happens after the pruning:

3 nodes omitted for budget: legacy-batch-job, vendor-sftp-quirk, 
old-retry-policy

Every omitted id is printed. Always.

This is the rule I am most confident about, because silent truncation is the specific failure that reads as success. An agent receiving eight of eleven notes, with no indication that three are missing, reasons as though it has the full picture and answers with the confidence that implies. And the three you dropped are the ones it needed — not out of pessimism, but because you dropped them for being peripheral to the query, and peripheral to the query is exactly where the surprising constraint lives.

Prune order is deepest-first, then least-connected:

.sort((a, b) => b.depth - a.depth || a.degree - b.degree || ...)

Depth is distance from what was actually asked about. Low degree means the node is unlikely to be a hub anyone needed. The final tiebreak is by id, so the same query returns the same bytes every time — which is what makes the reindex-determinism test meaningful rather than decorative.

Rule 4: Constraints are never dropped

At any cap. In either tier. No exceptions.

const removable = nodes.filter((n) => n.depth > 0 && n.type !== 'constraint');

Two things are exempt from pruning: the root note you asked for, and every constraint.

The reasoning is economic rather than aesthetic. A constraint is the note that says the client will not approve a new database, or this service cannot call out to the public internet, or we tried Kafka here and the platform team said no. It is precisely the note that stops an agent from spending a dozen requests building toward an approach that was never going to ship.

Dropping one to save four hundred bytes trades the cheap thing for the expensive thing. The bytes are cheap. The dead-end implementation is not.

Which produces a situation the code has to be honest about. When the root and the constraints alone exceed the budget, the budget loses:

Note: 9,412 bytes returned, over the 8,192 budget, because constraints 
are never dropped.

Reported, not fixed. The fix would be dropping what is worth keeping.

The store is markdown. The index is disposable.

Underneath all four rules is one structural decision: the notes are plain markdown files with YAML frontmatter, and index.db is a cache you can delete at any time.

~/.agents/memory/
  notes/<type>/<id>.md     the source of truth
  notes/archive/           superseded and decayed notes; never deleted
  index.db                 disposable SQLite cache
  ROUTING.md               generated map of everything known

agent-memory index rebuilds the database from the notes byte-identically. The database exists because traversal in SQL is fast and traversal over a directory of files is not — the graph engine is a recursive CTE with a depth bound and UNION rather than UNION ALL, which is what keeps a contradicts cycle from recursing until SQLite gives up. There is no graph layer sitting on top of SQLite. The CTE is the graph engine.

But nothing important lives only in the index. If SQLite corrupts, you lost a cache. If you uninstall the tool, you are left with a directory of readable markdown that stays useful with nothing installed at all. What your knowledge lives in should outlive what indexes it, and a proprietary binary store fails that test on day one.

That property is also what makes the whole thing installable in a locked-down environment, which is why I built it in the first place. node:sqlite has shipped inside Node core since 22.5, so the index needs no package, no service, and no network. On a managed desktop, "a Node script" and "a new database" are two entirely different conversations with two entirely different outcomes.

What I deliberately did not build

Capture is explicit. You invoke it, or the handoff skill does. Nothing fires on its own.

That is a real constraint and I picked it on purpose. Ambient capture — a background process watching your session and deciding what is worth keeping — is the feature everyone asks for, and it is the feature most likely to fill the store with confident noise. Every honesty rule above gets weaker as the volume of low-quality notes rises. A system that captures ten good notes a week beats one that captures four hundred, and four hundred is what you get when a model decides on its own what mattered.

Also not built, for now: team sharing, multi-machine sync, and an MCP server. The MCP server would read this same store, so it is an addition rather than a rewrite, which is the main thing I wanted to keep true.

And one thing is genuinely unproven. The test that matters is the cold read — a fresh chat, in a repo untouched for a month, answering correctly from the routing digest alone. That needs real elapsed time and cannot be faked in a test suite. Seventy-one tests pass on Linux, macOS, and Windows across Node 22 and 24. Not one of them proves the thing I actually want to know.

The part worth stealing

If you are building memory into an agent workflow — your own, or something you ship — the four rules generalize past this project:

  1. Show age where the knowledge is used, not in a dashboard nobody opens.
  2. Make the sanitizer’s failure mode “nothing written,” and refuse to add the bypass flag.
  3. Print what you dropped. Silent truncation reads as full coverage.
  4. Decide what is never droppable before you need the budget, because you will make a worse choice under pressure.

None of these are hard to implement. All four are easy to skip, and all four are invisible when they are working. Which is exactly what makes them worth writing down.
